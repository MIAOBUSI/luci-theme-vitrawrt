# Argon Study Notes

These notes capture what VitraWrt should learn from Argon-style LuCI themes without repeating the previous architectural mistake.

## Useful Lessons

- A LuCI theme should own the shell: navigation, background, typography, color scheme, login page, and broad visual consistency.
- Theme CSS should be conservative around LuCI runtime content because many pages are generated by LuCI JS after page load.
- Supporting both modern ucode templates and legacy Lua templates improves compatibility across OpenWrt and ImmortalWrt releases.
- A theme can make native pages feel calmer without changing their information architecture.

## Boundary To Preserve

Native LuCI pages are not Dashboard.

Argon-style theme polish must not become page ownership. VitraWrt must not treat these native pages as dashboard canvases:

- `/admin/status/overview`
- `/admin/system/system`
- `/admin/network/network`
- `/admin/network/firewall`
- vnStat or other plugin-native routes

## What Not To Copy

Do not use theme CSS/JS to:

- Hijack native LuCI routes.
- Turn the native overview page into a dashboard.
- Re-layout `ifacebox`, `network-status-table`, CBI tab panels, firewall tables, or plugin graph pages as custom cards.
- Force hidden, dependency-controlled, hover-only, or inactive tab content to become visible.
- Build service widgets in the theme layer.

## VitraWrt Direction

Stage 1R:

- Safe theme foundation.
- Conservative native page styling.
- Floating sidebar and responsive shell.
- Runtime regression tests that protect LuCI behavior.

Stage 2:

- Independent `luci-app-vitrawrt-dashboard`.
- Menu entry: `VitraWrt -> Dashboard`.
- Route: `/admin/vitrawrt/dashboard`.
- Dashboard views and data are implemented as app logic, not theme CSS.

This keeps VitraWrt coherent: native LuCI pages remain dependable, while the future dashboard can be intentionally designed without breaking OpenWrt's existing administration pages.
